# AI Weekly Summary

The "data story" feature — a plain-language weekly reflection generated from a
user's real usage. This is the first revenue-hook candidate for a pro tier.

## Overview

On the `/analytics` page, the **Weekly Insights** card aggregates a week of data
and produces:

- **Headline** — one line summarizing the week
- **Narrative** — 2-4 sentences of reflection
- **Patterns** — 3-5 grounded insights about focus, energy, task patterns
- **Suggestions** — 3-4 actionable next-week ideas

## Data grounding

The summary pulls from the week (Monday → Sunday, local time):

- `focus_sessions` — minutes, sessions, completion rate, best day/hour
- `tasks` — completed count + titles
- `checkins` — count, daily intentions
- `reflections` — prioritized sections (accomplishments, wins, blockers, etc.)
- `north_star` + `core_values` — for grounding language toward the user's vision

The LLM is instructed to never invent numbers, write in the second person, and
avoid em dashes.

## Two paths

1. **AI** — when `OPENAI_API_KEY` is set, it calls an OpenAI-compatible
   `/chat/completions` endpoint and parses the JSON response.
2. **Rule-based fallback** — when no key is set (or the call fails/timeouts),
   it returns a deterministic summary built from the same data. Keeps the
   feature working for free and makes it fully testable.

Both paths always carry the real `stats` object, and the UI shows which path
generated it (`generated by <model>` vs `rule-based (AI not configured)`).

## Provider flexibility (cost)

No hard dependency on OpenAI. Any OpenAI-compatible provider works via env:

| Env | Default | Notes |
|-----|---------|-------|
| `OPENAI_API_KEY` | — | Set to enable the AI path |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | Point at DeepSeek etc. |
| `OPENAI_MODEL` | `gpt-4o-mini` | e.g. `deepseek-chat` |

DeepSeek example (much cheaper than OpenAI):

```
OPENAI_BASE_URL=https://api.deepseek.com/v1
OPENAI_MODEL=deepseek-chat
```

The call uses plain `fetch` (no new npm dependency), a 15s timeout, and
`response_format: { type: "json_object" }` to force parseable output.

## Architecture

- `lib/weekly-summary.ts` — data aggregation + LLM call + fallback. Pure logic,
  unit-tested.
- `app/api/weekly-summary/route.ts` — authenticated `GET`. Validates the
  `Authorization: Bearer <jwt>` header, then runs queries via a **service-role**
  client (identity already verified by the JWT). Server-side RLS would otherwise
  block reads, since the anon singleton has no attached session.
- `components/analytics/WeeklyInsightsSection.tsx` — the UI card; Generate /
  Refresh button with loading and error states.
- `tests/lib/weekly-summary.test.ts` + `tests/api/weekly-summary.test.ts` —
  cover the deterministic fallback, stats aggregation, and route auth/error paths.

## Security notes

- The LLM API key lives **only** server-side (`app/api/weekly-summary/route.ts`),
  never in the client bundle.
- The route verifies the user's JWT before generating, and scopes every query to
  `user_id`. The service-role client does not expose a general data endpoint.
- The prompt is server-built; user data (reflections, task titles) is sent to the
  configured LLM provider as-is. Consider redaction/privacy notice if sensitive
  journal content is involved.

## Verification

To confirm the AI path end-to-end: set `OPENAI_API_KEY` (or a DeepSeek key +
base URL), run `pnpm dev`, log in, open `/analytics`, click **Generate**, and
confirm the summary's source tag reads `Generated by …` rather than the
rule-based fallback. With no key set, the button still works and returns the
fallback.
